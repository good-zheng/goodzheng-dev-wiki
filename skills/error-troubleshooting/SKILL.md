# 报错排查流程

适用范围：通用入口，任何排查先走本流程；确认属于前端或后端场景后，再进入特化分支（前端见 [frontend-console-errors](../frontend-console-errors/SKILL.md)，后端见 [backend-api-troubleshooting](../backend-api-troubleshooting/SKILL.md)）。

## 排查步骤

1. **收集现象**：完整报错信息、堆栈、复现步骤、最近的相关变更（git log / 部署记录）
2. **定位范围**：根据堆栈锁定出错文件与行号；无堆栈时从报错文案反查日志来源
3. **提出假设**：列出 2~3 个最可能的原因，按可能性排序
4. **逐个验证**：用最小代价验证每个假设（加日志、打断点、读代码、比对配置），一次只改一个变量
5. **确认根因**：能解释全部现象（包括正常路径为何不受影响），才算确认
6. **修复与回归**：修复后验证原始复现步骤已通过，并检查同类位置是否存在相同问题

## 常见误区

- 不要只看报错第一行——根因常在堆栈最深处的自己代码里
- 不要在未复现前就改动代码——改完无法证明是修复生效还是偶发
- 不要一次改多处——无法判断是哪处改动起了作用

## 输出格式

排查结论按此结构汇报：

```markdown
## 根因
<一句话说明根因>

## 证据
- <验证步骤与观察到的结果>

## 修复
- <改动点与原因>

## 遗留风险
- <未覆盖的场景 / 建议补充的测试>
```
